# 研究策略真实对照：未证明新策略优于现有策略

2026-09-12，用户授权测试。**没有切换生产策略、修改日程或发送 Telegram。**

## 方法

- 两组均为真实 Nimbus AgentOS → Astra 主控 → Grok/xAI 搜索；社区发现只用 `x_search`，web 仅辅助原始来源核验。
- A：已部署 generation 6 的并行日程指令快照；B：`RESEARCH_QUALITY_DESIGN.md` 中事件级、48小时辅助发现与动态补缺的实验指令。
- 两组共同附加相同的固定窗口／测试隔离说明。主窗口 UTC 2026-09-11 11:58:45 至 09-12 11:58:45，辅助窗口从 09-10 11:58:45 开始。
- 每组最多 7 次真实研究请求、最多 4 并发、worker 900s。除指令外执行代码相同。实验进程内将 Research 上限从 8 收紧到 7，同时应用两组；生产源码和进程不变。
- 每组使用新的临时 PostgreSQL、合成身份、空记忆／历史／workspace；不连接生产 PG。沿用 Pi 认证，不读取／输出认证原文；只传沙箱配置，不向模型加载健康配置或数据。
- 随机选择执行顺序，抽到 A→B，顺序运行避免实验同时开启八路搜索。模型输入没有 Agents API 名称、公告链接或目标事件提示；提示 hash 在运行前固定。
- 每组创建一个隔离的普通后台任务；只生成测试 outbox，没有 Telegram sender。
- 私有保存 safe search projection、原生 session、telemetry、候选工作区和最终稿；没有新增原始成功 HTTP／认证日志。

这是一组冷启动实测，不是跨轮证据缓存验收，也不是固定搜索索引下的严格因果 A/B。

## 实际结果

| 项目 | A：现有策略 | B：实验策略 |
|---|---:|---:|
| worker 执行时间 | 384.066s（6分24秒） | 504.504s（8分25秒） |
| 外层研究请求 | 7 | 7 |
| 完成／报错 | 7／0 | 7／0 |
| 首批四路发现耗时范围 | 65–96s | 101–111s |
| 后续调用结构 | 三路核验并行 | 核验与补发现并行，再进行有依赖的核验 |
| Agents API 进入候选 | 是，先返回窗口内社区介绍 | 是，先返回较早的官方发布帖 |
| Agents API 进入最终稿 | 是，第3条，标注持续事件 | 是，第1条，标注持续讨论 |
| 最终条目 | 6 | 5 |
| 返回的内部 X / web 使用计数 | 25 / 13 | 20 / 16 |
| Telegram 实际发送 | 无 | 无 |

内部使用计数来自成功响应，不等价于费用；外层七次不是七次内部检索。调用完成也不等价于来源完整或事实独立核验。

B 确实执行了不同策略：产品发现用真实 `from_date=2026-09-10`，其他三路从 09-11 开始；中途对时间段／小案例偏科做了一次 `discover` 补缺，没有把广搜伪装成 `verify`。代价是多了一段依赖核验，整体更慢。

## 召回与编辑检查

A 收录：RubyGems 新归因讨论、Claude Code plugin eval、OpenAI Agents API、Cursor Projects、bpy.dev、Codex 等待 CI 的个人体验。

B 收录：OpenAI Agents API、RubyGems 新归因讨论、ApprenticeBench、bpy.dev、Loyverse MCP 使用案例。

两稿共同事件三项，合计八个不同事件／案例。B 的返回材料没有出现 A 找到的 plugin eval 与 Cursor Projects；A 的返回材料没有出现 B 的 ApprenticeBench 和 Loyverse 线索。**新策略没有支配旧策略，只是样本组成不同。** 这些名称的出现／缺失已核对返回正文，而不是只统计输出篇幅；它们全部是否应入选，尚无独立人工重要性标签和完整来源复核。

Agents API 两组都区分了原始发布与本期讨论：
- A 先取回社区帖，再取得官方公告材料，未将9月10日官宣写成今天发布。
- B 先取回官方帖，又补查窗口内讨论；最终明确没有取得新的能力或状态变化，只按持续讨论呈现。
- B 核验中出现“作者描述与引用 URL 不一致”的缺口，主控追加定点核对后再采用。说明更宽的发现仍不能省掉引用语义检查。

额外的本地一致性检查发现：B 一个未入稿的安全案例，其 provider 声称发帖时间与 X post ID 的 Snowflake 编码相差约255秒。ID 解码只检查时间自洽，不证明帖子存在、作者或内容属实；不可把它升级为独立事实核验。A 的可解析结构化候选未发现大于60秒的此类偏差，也不证明其新闻全部准确。

## 必须修正的解释

此前生产重跑未返回 Agents API；这次 A 使用同一策略、同一截止窗口，却成功返回并收录。因而：

- “24小时条件会必然排除这件事”不成立：窗口内的社区讨论仍能把较早的官宣带回来。
- 实际观察到的是主控查询、Grok 检索／摘要和索引条件下的**端到端结果波动**。这次没有固定逐字查询、随机种子或搜索索引，不能进一步把波动单独归因给某一层。
- 已有证据跨 run 不可复用、对已知重要事件缺乏去向检查，仍是代码支持的系统性缺口；但本轮未实现或测试其修复效果。
- 扩大辅助发现窗口是合理假设，本轮不证明它能提高整体重大事件召回，更不能以找回一个已知案例宣布成功。

## 决定与下一步

**不因本轮结果替换生产指令，不宣布研究质量已修复。** 两组都超过当前5分钟准备 lead，也没有新的准时保证。

下一步最有区分力的验证：
1. 为多个日期／事件建立人工审阅的参照池，明确重要性、时间与来源支持；不要把 A/B 任一稿当真值。
2. 冻结来源做“候选进入之后是否被丢弃”的回放，和实时发现测试分开。
3. 实现／测试有权限范围的事件证据连续性与已知高影响事件去向检查；先同一研究集合跨 run，再解决跨前台后台公开来源的授权提取。
4. 需要更多真实查询时，另设有上限的重复样本；不自动重跑直到某策略获胜。
