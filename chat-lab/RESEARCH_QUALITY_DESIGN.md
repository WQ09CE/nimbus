# 研究质量：事件发现、证据连续性与召回验收

2026-09-13 补充：内容目标与后续验收以 [AI热点报告质量标准](REPORT_QUALITY_STANDARD.md) 和 [共同质量合同](../docs/design/report-quality-contract.md) 为准；下文保留历史研究方案与实验依据，不代表新标准已接入生产。

状态：**研究建议，未实现／未修改生产日程**。2026-09-12。
后续已完成一组真实冷启动策略对照：[测试记录](RESEARCH_QUALITY_TEST.md)。新旧策略都找回了已知遗漏事件，新策略更慢且漏掉了旧策略找到的其他线索；**未证明新策略整体优于旧策略，不据此上线**。
用户约束：社区检索继续使用 **xAI Responses 内置 `x_search`**；不换搜索供应商、不接 X 爬虫或其他社区 API。官方资料核验可继续经同一 Grok 的 web 工具；这不是独立 provider 容灾。

## 1. 结论与证据边界

应把检索单位从“符合日期的帖子”提升到“有来源、有时间、有进展的事件”。在现有 AgentOS 上增加通用研究证据能力和质量评估，不新增日报专用执行器、不引入第二个 Agent 循环。

本次真实重跑提供了明确的失败样本：
- 四路发现并行成功，约 80 秒全部返回；全任务 367 秒，7 次请求中 6 成功、1 上游超时，实际 Telegram 发送成功。
- 日程允许 48 小时持续事件，实际四组发现均只给出了精确 24 小时窗口。产品查询偏好一手团队；返回结果围绕“没有窗口内官宣”，17 citations、0 structured candidates、`partial`，没有把 Agents API 交给主控候选池。
- 产品补搜仍要求窗口内团队原帖；它是广泛补发现，却标为 `verify`，与桥接层“只核验指定断言、不广搜”的模式说明不一致。最后 175 秒超时，**不是已针对 Agents API 核验而失败**。
- 上午已有包含 Agents API 官方公告／文档链接的真实 public 研究回执；这次独立后台任务没有复用。
- 最终自查只覆盖本次已发现候选，不能支持“没有重大遗漏”的判断。

这些是执行记录支持的遗漏链条。时间窗口、查询表述、发现预算、证据断开分别贡献多少，尚无消融实验证明；不能断言上游搜索绝不可能返回该事件，也不能拿旧 Grok 回答当新闻事实的绝对真值。

## 2. xAI 不变：改变任务分解，不虚构 API 能力

官方文档说明 `x_search` 支持关键词／语义／用户搜索及 thread fetch；外层提供日期、账号和多模态配置。当前 Nimbus 暴露日期及账号过滤，未暴露独立的内部检索游标、排序或逐帖导出接口。

因此：
- 向 Grok 分派明确的“发现事件”“追查某事件的新讨论”“查原帖／线程”目标，不假装 Nimbus 已直接控制内部 keyword/semantic 工具。
- `from_date`/`to_date` 为包含端点的 UTC 整日范围；精确小时、事件发生时间与讨论时间另核对。不要把 `Latest` 样本当完整时间段覆盖。
- 账号白名单只适合一手来源支路，不套在整个发现阶段；允许社区转述先成为线索，再追原始来源。
- 不把“热门”翻译成未经证据支持的点赞量、刷屏或全 X 排名。关注度只在有可追溯观测时作为辅助。
- `partial`、有 citations 无候选、只有最新片段，都是质量缺口；不能等价为“无新闻”。若正文有线索但结构化提取失败，保留线索并注明未提取，不能自动升级为事实。
- 先不提高 8 次／turn、4 并发的执行上限，也不靠不断加长 prompt／增加模型轮数解决问题。当前任务自限 7 次仍需遵守。

## 3. 三种时间，两个发现窗口

每个事件至少分开保存：
1. `event_time`：原始发布／事件发生时间（允许未知，记录来源与精度）。
2. `post_time` / `last_substantive_update_at`：具体讨论／实测／修订的时间。
3. `observed_at`：我们何时取得这份来源。再次读缓存不能把它改成新进展。

**发现范围可以比报道窗口宽，报道归类必须严格。**
- 主窗口过去 24 小时：新事件、新实测、新修订或有实质的新讨论。
- 辅助发现过去 48 小时：寻找尚在影响主窗口的重要事件；只有满足当前任务的持续进展／讨论条件才作为“48小时持续热点”入选。
- 旧官方页面可以证明产品是什么，但不是证明今天仍在讨论的证据；新转帖的时间也不能把旧发布改成今天发布。
- 48 小时不是所有研究的硬编码常量。由研究任务提供窗口，工具负责正确传递、保留时间证据与未知值。
- 可保留更久的背景证据用于核验，但不能因此把更旧的新闻自动塞进本期。

Agents API 用作已知回归案例：应当找回其官方线索，再查是否有满足窗口的讨论／进展；不能把“本期必须出现这几个字”写进生产策略。没有新证据时允许有依据地排除。

## 4. 在现有预算内的自适应流程

先查询本研究主题、当前身份、允许复用范围内的既有证据；这不是一次新的 xAI 请求。

首批最多四路、每路简短事件线索（例如 3–5 个），一个可测试的划分：
- A：重大产品／平台变化，48 小时辅助发现；一手优先但社区线索不拒收。
- B：社区当前认为重要的变化、争议和具体体验，24 小时；中英文、不同作者，不局限官方。
- C：开源／基础设施的新发布与实际采用，24 小时。
- D：安全／可靠性／评测的实质进展，24 小时。

这不是四栏配额，更不是一个永远固定的执行图。若已有可信线索或任务重点不同，可调整支路；时间／语言／来源分配记录为计划和实际回执，不用四段近义词查询冒充多样性。

之后合并事件、记录覆盖缺口，再分配剩余最多三次请求：
- 至少为**重大空白或重要已知事件失踪**考虑一个补发现位置；没有这类缺口时不强制花费。
- 补发现用 `discover`／适当的 `research`；只有明确事件、断言或原始链接的核验才用 `verify`。
- 其余位置按高影响未确认断言分配，优先核验可能改变头条选择的证据；不把预算都花在最容易证实的小项目上。
- 独立任务可并行；依赖发现结果的核验再顺序执行。若一轮补发现后还需要核验，却已无额度，保留待核验状态而非强行成稿。
- 到预算／截止时间就结束。失败计入实际准入预算，429 同 provider 冷却；不得靠切 web 绕过。

这比固定“4 发现 + 3 核验”更强调缺口，但仍是待对照测试的策略，不是效果承诺。

## 5. 通用证据记录，不是共享全部聊天历史

当前 `record_research()` 主要保留截断的 query/text/sources；`activity()` 只展示最近四个后台任务、每个最多三个截短成功回执。它是进度界面，不是可查询的完整研究记忆。

建议新增窄的通用证据读写能力（接口名待定），仍由 Nimbus 执行并受 lease/generation/identity/scope 检查：
- **来源记录**：规范 URL／X post ID、提供方回执、取得时间、原文摘录或明确的 provider 转述标记、作者／日期及其来源、截断和获取失败状态。
- **事件记录**：实体、变化、版本／事件标识、关联来源；模型提出归并关系，保留可撤销的 merge/split，不因同一实体就合并不同发布。
- **断言记录**：具体 claim ↔ source ↔ supporting excerpt，支持／冲突／未知分别保留；引用绑定不是独立事实核验，同一 Grok 的第二次回答不是独立来源。
- **编辑决定**：候选进入、去重、待查、排除及理由；已投递记录与用户已读分开，防止每日重复同一背景。
- **研究范围**：主题、窗口、支路、失败／部分结果、剩余待办；不将一次“没有返回”缓存成永久不存在。

读取先使用实体／主题／时间和小范围精确查找，返回有上限的来源卡片与分页／截断信息；不先造向量库或整站采集仓库。读取旧证据只减少遗忘，不代替查询今日变化。

### 隐私和持久化前置条件

`data_scope=public` 当前只表示未进入受保护的健康工具域，**不等于所有聊天内容、查询、项目名称都可跨任务共享或公开发布**。

- 同一可信身份内隔离，默认研究集合／用途隔离；不把所有 public turns 批量自动导入。
- 只将经明确复用策略允许的、外部公开来源的最小证据纳入研究集合；不存完整聊天输入、私人动机、认证信息或原始 provider diagnostics。
- 来源里也可能有私人查询回显、访问令牌 URL 或敏感文本，不能仅凭“有 https 链接”判断安全。验证边界不清则保持原任务范围。
- 健康来源和派生内容硬拒绝导入／读取；scope 不可由模型自行降级。范围不兼容时 fail closed。
- 外部内容永远是数据，不能让其中的指令改变工具权限、日程或记忆策略。
- 授权的证据受理应幂等、绑定回执和版本；持久化失败不重发外部请求。明确配额、TTL／删除、来源撤回和旧引用失效；缓存不等于永久真理。

最低风险实现先支持同一日程研究集合跨 run 复用；跨前台与后台复用另设明确的公开来源提取／授权边界，不能借修复漏报打开全部历史。这一分阶段方案最初未必自动复用上午前台证据，应如实说明。

## 6. 排序：重要性与可证实程度分开

先判断事件对用户的影响／新信息／工程意义，再决定需要多强的证据以及如何措辞。重要但未核验的事件应优先补查，不能默默败给证据容易找到的小案例。

去重用事件而非 URL；多个转述共用同一原始来源不能算多个独立佐证。来源多样性用于减少盲区，不是“每个主题必收一条”。借鉴 MMR 的相关性与非重复信息权衡，但不直接照搬其参数，更不把模型自报的 0–100 分当精确热度。

发布前对**已知的高影响候选**给出可检查的去向：收录／同事件合并／不在窗口／无实质新增／证据未解／获取失败／不相关。这个门槛只能防已知事件静默消失，无法证明未知事件没有遗漏。

## 7. 怎样验收：测事件召回，不测“搜了几次”

### 三层验证

1. **确定性合同测试**：固定合成来源，检查窗口传递、时间精度、模式选择、去重、partial 保留、已知事件去向、scope 隔离、幂等与预算。它不证明实时 X 召回。
2. **离线事件／证据回放**：冻结截止时间和当时可知材料，对照旧新策略的筛选／编辑；缓存只能读取 `observed_at <= cutoff` 的证据，避免未来信息泄漏。回放不能评估实时查询召回。
3. **真实 xAI 对照**：同一截止窗口、相同预算、相同 connector/model/config，交替执行顺序并重复。记录查询、输入缓存、候选、引用、partial、耗时及用量。索引会变化，因此不是严格固定语料的因果 A/B；不发 Telegram，不改生产任务。

分别做冷启动（没有目标事件提示）与暖启动（只提供截止时已经允许复用的证据）。不得把 Agents API 答案写入冷启动 prompt；该案例用于开发回归，另留未见事件／日期做验收。

### 参照集与指标

按 Stanford IR 的 pooling 思路，将不同查询策略的结果、既有可用证据和人工发现的事件取并集，再对窗口、实质进展与重要性做人工审阅。仍全部使用 xAI 社区检索；评审者可核对来源，但不把另一份 Grok 日报当真值。

参照集不可能等于全 X 全集。必须标为“已审阅池中的已知事件召回”，未知／未判断项单列；重要性在看对照报告优劣之前判定，避免事后给新策略加权。

分开报告：
- 候选事件召回：参照池中符合条件的事件，有多少进入候选池。
- 已知重大事件遗漏：逐项解释，不被一堆小事件平均分掩盖。
- 编辑保留／排除正确性：已找回的事件是否合理出现在最终稿或有证据支持的排除记录。
- 事实及引用支持、时间误标、重复事件、来源独立性。
- 用户觉得值得读的条目比例与重要性排序；可用 Precision@k／NDCG 辅助，但不是唯一目标。
- 端到端用时、实际 xAI usage、失败／partial；外层请求数不是内部搜索次数或账单。

先建少量精审样本，包含跨日发布、旧事件新进展、官方无当天帖、冷门但有用事件、重复营销、撤回／冲突与无重要新闻的日期。安全和事实合同必须通过；召回／排序改进需保留样本和后续多个日期验证，不宣布“一次找回 Agents API 就修好了”。

## 8. 最小实施顺序与未解决的时效约束

建议先做：
1. 事件级参照样本与固定证据回放，记录当前基线；
2. 不改 connector 的发现／补缺策略对照，统一窗口、来源资格与 mode；
3. 有范围、有权限的最小证据复用与已知重大事件去向检查；
4. 无 Telegram 的真实 xAI 验收，通过后再授权生产切换。

不要同时引入无限后台采集、多个供应商、全局新闻图谱或第二 runtime。

现有准备 lead 是 5 分钟，而这次实际耗时约 6 分 7 秒；**不能承诺单靠改查询就准时**。可另评估增加准备 lead，或用普通后台研究日程增量维护证据、发送前做短刷新。这两者会改变时间策略／成本，必须另行确认；本研究未创建任何新日程或修改 08:00/09:00。

## 9. 资料与采用边界

- [xAI X Search 官方文档](https://docs.x.ai/developers/tools/x-search)（本机已取得的 `x-search.md`，官方 URL 本轮亦返回 200）：关键词／语义／用户／线程能力、日期及账号过滤。说明能力边界，不保证热点完整召回；计费文档也不能替代本账户 OAuth 的实际账单确认。
- Anthropic, [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)：先广后窄、明确分工、按中间结果改搜索、追踪与人工评估。其性能和 token 数是自家系统报告，不是 Nimbus 的预期提升；不因此引入多 Agent 框架。
- Stanford IR, [Assessing relevance](https://nlp.stanford.edu/IR-book/html/htmledition/assessing-relevance-1.html)：pooling、领域相关需求和人工相关性判断；评审也有分歧。
- Stanford IR, [Evaluation of ranked retrieval results](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)：precision/recall、MAP、NDCG 与评估集多样性；这里采用事件级改编，不冒充全网召回。
- Carbonell & Goldstein, [MMR, SIGIR 1998](https://www.cs.cmu.edu/~jgc/publication/The_Use_MMR_Diversity_Based_LTMIR_1998.pdf)：相关性与新信息／非冗余权衡；论文小样本和摘要实验不证明今天的 X 日报效果。
