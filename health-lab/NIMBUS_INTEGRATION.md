## 1. 目标与非目标

让同一个 Nimbus Bot 能解释今天的健康摘要、回答短期趋势问题，并通过普通持久化日程每天发送身体快报。不是新增一个只会发送固定文案的健康Bot，也不是给模型一个能任意调用Garmin的代理。

- 生理计算、数据质量与历史比较在本地完成；主控模型负责基于事实解释。
- Garmin账号始终只走固定读取白名单；不上传活动、不修改Garmin记录。
- 不提供通用URL、SDK方法名、SQL、文件路径或模型可选账号。
- 不向工具沙箱挂载token、原始JSON、SQLite或本地健康上下文文件。
- 不复刻WHOOP，不拿Garmin高准备度直接当训练真值，不未经校准制造0–100分。
- 不改现有AI日报的schedule、generation、下次投递；新快报是独立的普通日程。

## 2. 数据路径与实际隐私变化

```text
Garmin CN
  ↓ 固定七类读取，正常本机token续期
本地采集进程（唯一持有Garmin凭据，复用health-lab独立依赖）
  ↓ 私有raw + SQLite，源版本与失败状态
本地归一化 / readiness分项 / 最小摘要投影
  ↓ 固定schema的Unix socket接口
Nimbus原生garmin工具（身份与执行权检查）
  ↓ 获授权的最小摘要
主控模型解释 → 既有有序outbox → 授权Telegram私聊
```

这是一次明确的数据使用范围扩展：**获授权的摘要会进入主控模型的请求，以及Nimbus相关本地会话/交付存储，最终进入Telegram**。不能继续声称所有健康信息都不出本机，也不宣称Telegram Bot会话端到端加密或主控供应商零留存。

原始响应、连续心率/HRV序列、GPS、身份标识和Garmin认证材料不随摘要发送。摘要只包含回答当前问题所需的数值、质量、分段比较及少量用户已提供背景。工具输出、模型会话、最终报告同样是敏感数据，不进入Git，不作为普通公开搜索的输入。

保留/删除需按位置分别说明：health-lab raw/SQLite、worker会话及诊断、PG报告/投递/备份、Telegram和供应商副本不共享一个删除开关；`/new`仅重置上下文，不是删除健康数据。已有权限控制不是加密、异机备份或全局retention。

## 3. 接口：原生工具优先，不先搭MCP

现有 `AgentEngine` 使用原生 `ToolRegistry`，Pi仅负责模型请求，不自动加载技能文件。因此增加一个原生 `garmin` 工具及受控客户端即可，无需给Bot安装整个第三方MCP或修改gVisor网络策略。

候选接口（均为Garmin账户读取；刷新允许产生本地缓存写入）：

| action | 模型参数 | 返回 |
|---|---|---|
| status | `{}` | 数据日期/新鲜度、当前设备分段、缺测/认证状态，不含秘密 |
| daily_brief | `{day?: ISO-date}` | 一个版本化日摘要与本地生成的事实段 |
| trends | `{days:7\|28\|90,end?:ISO-date}` | 已归档数据的有界分段趋势，不触发历史回填 |
| method | `{}` | 当前方法说明、规则版本、限制、分数是否已校准 |

身份、账户映射、as-of、刷新策略、deadline、当前attempt/slot由可信runtime注入，不来自模型参数。定时调用的目标醒来日期从计划slot和时区推导，防止补跑时随意用“现在”替换原目标。一般交互可以查历史，但范围有限且明确为回顾性分析。

初始边界建议：单次返回≤24KiB、每turn最多4次健康读取；不返回完整raw、逐点数据、文件路径、源账号/设备ID。趋势优先给聚合与少量异常日期，而非默认输出90行日明细。

### 进程与权限

- 本地gateway用私有Unix socket，不开放TCP监听；校验peer及部署时绑定的主体。
- 保留health-lab单进程SDK/认证隔离，不在长期运行的chat worker里调用会全局关闭logging的 `authenticate()`。
- collector与手工CLI共用归档锁；只允许一个账号同步任务在运行。
- **同UID分进程和0700不是抵御该UID恶意代码的强隔离**。模型可达工具不提供宿主执行/文件访问；进一步用可验证的worker挂载命名空间限制遮蔽健康秘密目录，或独立服务用户。若采用这种强化，必须实际验证worker及Pi子进程不可读，不把配置项本身当证明。
- socket映射是本地服务能力，不是Garmin只读OAuth scope；令牌仍可能拥有账户写权限。

## 4. 有界刷新，而不是聊天里跑90天同步

推荐由日程准备阶段触发“确保今日快照”的有界读取，不另外维护一份固定时间的采集cron。这样用户修改投递时间时，不必同时修改两套时钟。

1. 前台默认读取当前快照，快速返回。如果较旧，明确其时间；需要刷新时走已有后台任务机制，不把聊天lane堵住。
2. 定时后台可以等待一次刷新；默认仅重看最近3天及首日前一天HR，即已有22次业务读取。同步后生成新摘要，不每天回填90天。
3. 相同账号/范围single-flight合并，跨任务复用；持久化最近尝试与冷却，重启不能绕过限流。
4. 初始刷新预算建议150秒内、批次不超过22项、保持现有请求间隔；这是待实测调优的资源预算，不是网络耗时保证。不能同步阻塞async事件循环或lease renewal。
5. 认证/429/网络失败立即结束本批次，保留进度与安全错误类别，不由模型不断重试。认证失效只通知回本机登录，不在Telegram收密码/MFA。
6. 请求被取消或失去turn执行权，停止等待/禁止交付。共享collector可能仍完成已受理的账户读取并更新缓存；这不是续写失权turn，更不能宣称远端读取已撤销。

### 原子摘要与新鲜度

新增sync batch/快照manifest，使一个摘要绑定明确source observation IDs/hashes、各源fetched_at、计算截止点、归一化/方法版本。摘要临时写入后原子发布；读取不与长时间网络同步共持归档锁。失败不得把前一批好数据无标记地伪装成今日新数据。

区分：取得时间、睡眠实际起止、预期醒来日期、记录是否confirmed、是否完整、是否可能修订。刚刚fetch成功不代表手表刚刚上传或今天睡眠已经结束。要得到新数据，仍需要手表先同步到Garmin Connect；本地API不能强迫未联网的手表上传。

标准状态为 `complete / partial / pending_sync / stale / unavailable`。可以展示旧快照，但必须是明确标日期的历史背景，不能填入今天的恢复结论。白天尚未结束的日静息HR、午睡等不能伪装成晨间已完成结果。

## 5. Readiness契约：算法与解释分开

本地静态方法说明放在版本化的包资源里；核心禁止事项注入 `AgentEngine` 的受限健康上下文。`garmin.method`用于按需展开，不能靠把一份文件放进目录就假设Pi会自动读到。

真实设备映射、活动习惯与背景单独来自私有用户上下文，标注用户陈述的来源/时间。习惯不是每一次已验证发生的事件；缺少心率的活动不能反造心率或Garmin EPOC。

### 摘要最小契约（字段类型示意，不是真实数据）

```text
schema_version, snapshot_id, report_day, timezone
collected_at, computed_at, source_status, completeness
normalizer_version, readiness_method_version
device_segment_label, baseline_valid_nights, baseline_status
night: HRV, sleep-window-HR, sleep_hours, start/end
comparisons: past-only同设备/同算法的基线或明确标注的相邻夜描述性比较
reference: Garmin醒后准备度、睡眠分、可用的过去完整日静息HR
readiness: score=null, calibration_status, signals[], evidence_keys[], limitations[]
context: 最小必要活动/设备背景，reported_habit与confirmed_event分开
```

第一版继续沿用过去42天内至少28个同设备、同算法有效夜晚的基线门槛；新设备不足时只给有标签的描述性比较，不调用旧设备基线冒充新基线。新规则进入每日投递前要版本化及离线验证。

- 核心看当夜HRV与睡眠窗口HR的个人偏离，兼看两者是否同向、是否持续。极端高HRV或低HR不自动加分。
- 睡眠时长/规律/质量是独立展示维度；一般小时阈值不是已拟合的个人睡眠需求。
- Garmin sleep score/stress/Body Battery/readiness有共享底层信号，不重复叠成四票。
- 加入实际运动与主观体感作为恢复背景；不凭星期直接扣分，也不把固定每周发生的恢复需求按星期归一化掉。
- 夜间生理恢复与肌肉/关节恢复不是同一个变量，单晚HRV回升不等于完全恢复。
- 周期相关性不是医学因果证明，不诊断疾病，不把运动后的预期变化说成运动有害。
- **score=null时，模型不得自行输出“自定义恢复分82”等数值**。数字只能来自工具；当下输出证据与不确定性，不制造精确概率或置信度百分比。

后续用用户看分前的精力/酸痛等标签定义校准目标，做按时间留出的验证，与简单单指标及Garmin参考值比较。历史描述性回测不等于晨间前瞻预测，不能以“某天应该低分”作为循环验证的标签。

## 6. 每日快报与调度

建议初始投递时间为 **北京时间09:00**，等待手表/手机完成晨间同步；时间待用户确认。使用现有 daily schedule，默认提前5分钟准备，B/C执行，A继续聊天。无需把健康逻辑写进通用scheduler轮询。

固定日任务意图：取得当天健康摘要和必要的方法/背景；只根据有效数据给出一句总体观察、关键变化及一两项低风险建议。不搜索私人的健康数值，不臆造总分，不自动改变计划或Garmin账号。

日常文案建议150–250字，无Markdown表格，结构为：

1. 今天最值得注意的一件事；
2. HRV/夜间HR/睡眠的关键事实与比较依据；
3. 可能相关的实际活动背景（未确认参加则用条件语气）；
4. 一个可执行建议；必要时提示基线或数据不完整。

这是内容结构，不是预先编好“周几就发送哪句话”。身体快报有自己的日程和上下文；不与AI新闻任务共享健康内容。

关键数字由工具生成事实段；候选交付方案是一个有来源绑定的结构化报告，保留确定性数字，LLM只组织解释与建议。需要新增验证/渲染支持，现有引擎自由文本输出还不能提供这种保证。若解释输出违反分数/数据约束，则退回确定性事实快报，不发未经依据的数字。

当天数据没到：默认照时只发一次简短“昨夜数据未同步，暂不判断恢复”的快报，不拿昨天数据顶替，不长期占住后台worker，不默认追加多条补报。用户稍后自然语言要求更新可走独立即时任务，不移动日常slot。自动等待数据再推送需要另行设计事件/时限，不宣称当前日调度器已有此功能。

遵循现有唯一slot、generation/lease/outbox fencing和uncertain语义；不承诺网络模糊失败下绝对exactly-once。主机睡眠/离线时按现有四小时latest catch-up行为处理，冷启动和未来真实送达需单独验收。

## 7. 健康上下文不能顺手流进搜索

单靠prompt里写“保密”不足够。至少实现：

- 健康定时任务在可信任务策略中只允许 `garmin` 与 `clock` 等最小只读能力，不注册/授权search、workspace、通用memory写入或递归任务写入。
- `health_summary`是可信runtime赋予的数据范围标签，不由模型声明。工具结果、报告和进入历史的消息保留这个标签。
- 现有系统会把已发送后台报告注入聊天历史。不能原样沿用到所有任务：含健康信息的上下文禁止调用搜索/通用内容导出工具；普通公开研究上下文不自动加载健康报告数值。需要时从garmin按需读取。
- 混合“身体情况+公开研究”的请求需分开上下文，公开查询不携带健康报告/标签/私有背景。不能先让模型看完整健康历史，再假设它生成的搜索query一定干净。
- 健康定时任务隔离是一期硬门槛。交互中的标签传播/清洁上下文路由如果尚未实现，不宣称交互健康读取与公开搜索已安全混用，应暂不开放该混用路径。

这是对通用任务能力/数据范围策略的一个应用，不是把身体日报硬写成单独执行循环。PG新字段或关联表若必需，需owner migration并遵循既有停入口/排空维护流程。

## 8. 后续自然语言体感记录

另设 `health_note` 本地写入能力，**不是Garmin账号写入**。仅处理明确的用户记录请求，后台报告只能读取，不能替用户生成标签/修改活动历史。

- 日期、事件实际时间、录入时间、来源消息、主观强度、精力/酸痛等分开存。没有给数字的自然语言不能被擅自当成精确量表值。
- 记录score exposure；不能把“尚未发送”当成用户没看过手表，也不能把“已发送”当成用户真的读过。默认未知，仅在用户明确说明时标为看分前。
- 快报后反馈仍有价值，但不是无偏的盲填标签。可以让用户醒来先发体感，无需强制每日额外提醒。
- 不直接在worker里写SQLite后再赌PG lease仍有效。候选方案为在PG权威事务内记录有幂等键的受理事件，本地健康服务异步、去重导入并回写receipt。PG会因此持有最小体感记录，需纳入上述隐私范围。
- 跨库不是一个原子事务；接受、导入及撤销边界必须真实表述。未导入不能冒充已用于当前分析，重复Telegram update不应变成重复标签。

一期读快报可以先上线；体感写入是独立后续纵切，不阻塞首份报告，也不靠模型每次猜存储语义。

## 9. 实施切分与验收

### A. 本地摘要契约与隔离gateway

新增建议模块：health-lab的 `brief.py` / `gateway.py` / 版本化方法资源；固定JSON schema、快照manifest和single-flight刷新。复用现有provider/features/storage，不另复制Garmin认证栈。

验收：合成fixture；正确日期/跨午夜；不同设备不能混用；历史as-of；缺测/认证/429；缓存原子发布；并发合并；CLI锁冲突；限定刷新范围/预算；原始身份、token、异常ticket不能进入响应。

### B. Nimbus原生工具与最小健康任务策略

新增chat-lab的受控 `garmin_client.py`，接入 `AgentEngine` registry，工具前/返回前重新检查当前turn执行权与身份。异步IO不得阻塞心跳。健康错误只返回固定安全类别，collector原始异常不得进入chat-lab的明文bridge/runtime诊断。

验收：错误主体、伪造账号/路径/URL/SDK方法拒绝；cancel/lease过期/disable后不交付；模型注入不能转发健康fixture到search/workspace；数值绑定；上下文历史不能跨到新闻任务；garmin工具没有宿主Bash fallback。

### C. 端到端与生产投递

1. 合成health fixture + isolated PG/outbox；不发真实Telegram。
2. 已授权最小真实摘要经过主控模型解释的smoke，单独说明这是实际模型请求。
3. 维护部署：停入口、排空全部A/B/C、部署与必要迁移、验证lane/observe/现有日程不变；PG不随应用重启。
4. 一次用户明确请求的真实身体快报，核对工具事实、中文解释和私聊投递。
5. 确认发送时间后创建唯一新日程；未来一个真实slot实际送达另行验收，手工即时发送不能替代。

回滚只撤销新工具/健康任务入口及新健康日程；不删除raw/历史、不回滚已有AI日报、不伪造Telegram游标或自动重放失败任务。

## 10. 本次设计结论

推荐路线：**本地有界采集 → 本地可核验的最小摘要 → Nimbus原生工具 → 普通持久化日程**。

先让每天的事实和解释可靠、数据流边界明确，再校准个人readiness数值。以上是原设计门槛；后续获得明确实施授权后的部署与真实发送见 INTEGRATION_STATUS.md。
